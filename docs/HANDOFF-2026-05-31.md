## 1. The critical bug (headline)

**Symptom.** On a machine that had never run Agent-X, the first launch produced an
**empty database** — every feature failed with `no such table: documents /
memories / user_settings / oauth_credentials / …`. The app window opened and was
responsive, so the failure was silent at the UI level but total at the data level.

**Root cause.** App startup calls `AgentXDbContext.EnsureKeyApplied()` (to apply the
SQLCipher PRAGMA) **before** the migration runner. Opening that connection
**creates an empty `agentx.db` file**. `MigrationRunner.RunCoreAsync` then saw
`CanConnectAsync() == true`, treated the brand-new empty file as a *pre-migration
install*, and ran `AdoptBaselineAsync` — which **stamps the baseline (and later)
migrations as applied without creating any tables**. `MigrateAsync` then skipped the
table-creating baseline and threw `no such table: memories`, leaving a schema-less
database.

**Why tests didn't catch it.** The unit test `RunAsync_on_fresh_database_applies_all_migrations`
never opened the connection before running the runner, so `CanConnectAsync()` was
`false` and it took the correct `MigrateAsync` path — which is **not** what the app
does at startup.

**Fix** (`src/AgentX.Core/Data/MigrationRunner/MigrationRunner.cs`, commit `b65e78d`).
Baseline adoption is now gated on the database actually containing application
tables (new `HasApplicationTablesAsync`). An empty database falls through to
`MigrateAsync` and receives the full schema. Genuine pre-migration installs (real
tables, no `__EFMigrationsHistory`) still adopt the baseline as before. A new
regression test opens the connection **before** running the runner — mirroring
`EnsureKeyApplied` — so it reproduces the real startup sequence (fails before the
fix, passes after).

**Verification (end-to-end, on a truly clean profile).**
- Migration runner applied **all 11 migrations**; **40 tables** created
  (`documents`, `memories`, `user_settings`, `oauth_credentials`, `conversations`, …).
- **Zero** `no such table` / init-failure lines in the startup log.
- Full **install → launch → uninstall** of the shippable installer succeeded; uninstall removed the program dir cleanly.

## 4. How to reproduce the build / test / package

`.NET 8 SDK` lives at `C:\Users\Rock\.dotnet` (system PATH only has .NET 10), so
invoke it by full path. Shipping solution = `AgentX.sln`, **Release|x64**.

```powershell
$dotnet = "$env:USERPROFILE\.dotnet\dotnet.exe"

# Build (warning-free) + full test suite (1,804 tests)
& $dotnet build AgentX.sln -c Release -p:Platform=x64 --no-incremental
& $dotnet test  AgentX.sln -c Release -p:Platform=x64 --no-build --blame-hang-timeout 4m

# Publish self-contained (unpackaged WinUI) → publish\win-x64
& $dotnet publish src\AgentX.App\AgentX.App.csproj -c Release -r win-x64 `
    --self-contained true -p:Platform=x64 -p:WindowsPackageType=None -o publish\win-x64

# Build the offline installer (needs the model in models\ first)
& "$env:LOCALAPPDATA\Programs\Inno\ISCC.exe" installer\AgentX-Setup.iss
# → installer-output\AgentX-Setup-2.1.1-x64.exe
```

Notes: `dotnet test` can leave the xUnit host hanging after tests pass (issue **H1**
— native SQLitePCLRaw/LLamaSharp handles); always pass `--blame-hang-timeout`.
Windows PowerShell 5.1 `Get-Content`/`-Raw` mis-decodes BOM-less UTF-8 — use
`[IO.File]::ReadAllText/WriteAllText` for `.resw`/JSON, and prefer `[IO.File]`/`[IO.Directory]`
methods over `Remove-Item` (the sandbox blocks `Remove-Item` on unresolved variable paths).
