# Agent-X v2.0 — ANN Vector Scaling (HNSW) Design Spec

**Date:** 2026-04-15
**Feature:** #9 — ANN Vector Scaling
**Priority:** P1 (Foundation — Performance is Trust)
**Effort:** Large (4-6 weeks)

---

## 1. Problem Statement

`SqliteVecStore.SearchAsync` performs O(N) full scan — loading all embeddings from SQLite into C# memory and computing cosine similarity against every vector. At 100K embeddings, search latency exceeds 500ms. This is a scaling wall that undermines user trust.

## 2. Solution

Add an HNSW (Hierarchical Navigable Small World) approximate nearest neighbor index that provides sub-50ms search at 100K+ embeddings with >95% recall. The HNSW index is maintained in-memory alongside SQLite persistence.

### Library Choice

**HNSW** NuGet package (v26.4.177) by Curiosity — 105K+ downloads, pure C# implementation, no native dependencies, supports cosine similarity distance, configurable M and ef_construction parameters, serializable index.

## 3. Architecture

### Hybrid Storage Model

```
SQLite (vec_embeddings)     ← Persistent truth (survives restart)
       │
       ▼
  HNSW Index (in-memory)    ← Fast approximate search
       │
       ▼
  SearchResult → metadata join via EF Core
```

- **SQLite** remains the source of truth for all embeddings (insert, delete, count)
- **HNSW index** is built from SQLite on startup and kept in sync on insert/delete
- **Search** uses HNSW for >10K embeddings, falls back to linear scan for ≤10K
- **Index** is serialized to disk after rebuild for fast warm-start

### Class Design

```
IVectorStore (existing)
    │
    ├── SqliteVecStore (existing — fallback for <10K)
    │
    └── HnswVectorStore (NEW — HNSW-backed)
            │
            ├── SQLite connection (persistence)
            ├── HNSW index (in-memory)
            ├── Index file (disk persistence)
            └── Auto-rebuild on startup
```

## 4. HnswVectorStore Implementation

### Initialization Flow

```
1. Open SQLite connection (same as SqliteVecStore)
2. Check for existing HNSW index file on disk
3. If index file exists AND embedding count matches → load index
4. If index file missing OR count mismatched → rebuild from SQLite
5. Log index build time and embedding count
```

### Search Flow

```
1. If embeddingCount ≤ 10K → delegate to SqliteVecStore.SearchAsync (linear scan)
2. If embeddingCount > 10K AND HNSW index loaded → HNSW search with ef_search
3. If HNSW index unavailable → fall back to linear scan with warning
4. Return results in IVectorStore format
```

### Insert Flow

```
1. Insert embedding into SQLite (same as SqliteVecStore)
2. If HNSW index loaded → add item to HNSW index
3. Mark index as "dirty" (needs serialization)
4. Periodically serialize dirty index to disk (on OptimizeAsync or shutdown)
```

### Delete Flow

```
1. Delete embedding from SQLite
2. Mark HNSW index as stale (HNSW doesn't support efficient single-item deletion)
3. On next search, check staleness. If >5% of index is stale → rebuild
4. For small deletions, mark items and filter from search results
```

### Index Persistence

```
File: {StoragePath}/hnsw-index.bin
Metadata: {StoragePath}/hnsw-index.json (count, version, M, ef_construction, dim, created_at)
```

## 5. Configuration

### AppSettings Fields

```csharp
// HNSW Vector Search
public bool EnableHnswIndex { get; set; } = true;
public int HnswM { get; set; } = 16;              // Connections per node (default: 16)
public int HnswEfConstruction { get; set; } = 200; // Build-time search width (default: 200)
public int HnswEfSearch { get; set; } = 50;         // Query-time search width (default: 50)
public int HnswFallbackThreshold { get; set; } = 10000; // Use linear scan below this count
public int HnswRebuildThreshold { get; set; } = 5;      // % stale before auto-rebuild
```

## 8. Migration Path

- Existing `SqliteVecStore` remains unchanged and functional
- `VectorStoreFactory` selects implementation based on embedding count and settings
- No data migration needed — both stores use the same SQLite table
- HNSW index file is created automatically on first startup
- If HNSW index is corrupted, it auto-rebuilds from SQLite

## 9. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| HNSW NuGet package API changes | Pin exact version, wrap in IHnswIndexService |
| Memory usage at scale | Monitor, add index eviction for low-memory scenarios |
| Index corruption | Auto-rebuild from SQLite on mismatch detection |
| Slower inserts (index maintenance) | Batch inserts, mark dirty, serialize later |
| HNSW doesn't support efficient deletion | Mark stale, threshold-based rebuild |
