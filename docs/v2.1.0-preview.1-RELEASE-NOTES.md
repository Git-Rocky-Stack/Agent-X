# Agent-X v2.1.0-preview.1 "Bedrock" — Release Notes

**Status:** Preview (pre-release)
**Released:** 2026-04-17
**Base branch:** `phase1-bedrock`

## Overview

v2.1.0-preview.1 is the **data-layer hardening slice** of the "Bedrock" release. It ships two foundational pieces — EF Core migrations and SQLCipher at-rest encryption — so all subsequent work (audit log, Memory, MCP) runs on disciplined, encrypted storage.

**Scope carved out of this preview:**

- **C14 Audit Log** — rescoped to **v2.1.5** (follow-on hardening release). The HMAC-chained audit log is a Phase 2 Memory prerequisite; shipping it on its own release lets the encryption layer settle on real user vaults first.
- **A1 Multi-Language UI depth, A2 Keyboard-First Power Mode, B1–B7 service/VM splits** — remain targeted at v2.1.0 (final). Plans to be written phase-by-phase per the magnum opus cadence.

## What's in this Preview

### EF Core Migrations (B9) — production-ready

Database schema changes now ship via EF Core migrations under `src/AgentX.Core/Data/Migrations/`. Pre-B9 installs (which used `EnsureCreatedAsync`) are auto-adopted at the `InitialBaseline` migration on first launch so existing user data is preserved.

- `IMigrationRunner.RunAsync()` replaces the ad-hoc `EnsureCreatedAsync` + manual `ALTER TABLE` block
- Baseline adoption for pre-migration installs (zero-data-loss upgrade path)
- `IMigrationRunner.GetPendingMigrationsAsync()` for future UI surfacing of pending schema work
- `AgentXDbContextFactory` design-time factory for `dotnet ef` tooling

### Database Encryption (C13) — production-ready

Your vault can now be encrypted at rest using SQLCipher 4 (AES-256-CBC).

- **Automatic key management** — a transparent DPAPI-wrapped key tied to the Windows user, available to every user (a legacy passphrase mode using PBKDF2-HMAC-SHA256, 600,000 iterations, is still honored for vaults provisioned by older builds)
- **Raw-bytes key delivery** — every connection applies the key via `PRAGMA key = "x'<hex>'"`. The `Password=` connection-string shortcut is never used because it silently KDF-derives a *different* key
- **One-shot plaintext → encrypted migration** via SQLCipher's `sqlcipher_export` with atomic file swap and rollback-on-failure
- **Out-of-DB key state** (hotfix merged 2026-04-17) — encryption key state lives at `%LocalAppData%\AgentX\encryption.info.json`, not inside the encrypted DB. Holds storage mode, DPAPI-wrapped key (DpapiWrapped mode), and salt (UserPassphrase mode). This breaks the startup chicken-and-egg so both unlock paths work at launch before any DB access
- **Settings UI** to enable encryption with a single transparent toggle (available to every user)
- **Startup unlock flow** reads the `IEncryptionStateFile` marker first, derives the key via `IDatabaseKeyService`, applies it via `AgentXDbContext.EnsureKeyApplied()` before the migration runner touches the DB
- **Wrong-passphrase recovery loop** with SQLite ErrorCode-26 (`file is not a database`) detection

Disabling encryption is not supported in this preview — restore from a pre-encryption backup to revert.

## Changes to Previously Announced Scope

### C14 Audit Log → moved to v2.1.5

The C14 implementation plan is fully written and worktree-ready (`.worktrees/c14-audit-log/`), but it won't ship in v2.1.x preview stream. Reasoning:

- C13 encryption is a large, security-critical landing — users should have time on it before an audit subsystem layers on top
- Shipping C14 in its own minor gives it a cleaner release narrative and isolated regression surface
- The audit key provisioning story is simpler when C13's key-storage architecture has settled on production feedback

C14 remains a **Phase 2 Memory prerequisite** — it will ship before Memory regardless of v2.1.5 timing.

## Breaking Changes

None for users who do not enable encryption. Users who enable encryption will have their database atomically converted on toggle; a `.plain.bak` backup of the plaintext database is retained only through the atomic-swap critical section and removed on success.

## Upgrade Notes

- First launch after upgrade adopts the `InitialBaseline` migration automatically — no action needed
- Encryption is opt-in. Encryption uses a key tied to your Windows account, so there is normally no passphrase to remember; however, if a legacy passphrase-protected vault is in use and the passphrase is lost, the database cannot be recovered — back up first via **Settings → Backup & Restore**
- Pre-release binaries install side-by-side with v2.0.0; your existing vault will be upgraded on first launch

## Known Issues

- **Test-host shutdown hang** (`H1`) — the xUnit test host does not exit cleanly after all tests pass due to native library handles (SQLitePCLRaw / Whisper.Net / LLamaSharp). Tests themselves all pass in ~6 seconds; CI runs use a `blame-hang-timeout` of 30s. Fix tracked as a Phase 1 hardening ticket.
- **`dotnet ef migrations add` workflow** — requires `-p:CopyLocalLockFileAssemblies=true` because the `net8.0-windows10.0.22621.0` TFM omits runtime packs from the build output. Pre-build with that flag, then invoke `dotnet ef ... --no-build`.
